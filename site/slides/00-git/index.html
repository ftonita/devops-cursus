Тема 00 · Git: основы

Git — не магия:
три зоны и граф коммитов

Новички видят два места — файлы и историю. Git видит три: между ними стоит индекс.

За ≈ 15 минут: как устроен Git, что делают ветки, и как откатить ошибку без паники.

Начать с вопроса в зал: «Кто коммитил, а потом понимал, что коммитил не то?» Пообещать, что к концу темы эта ситуация станет разбираемой.

Подсказать, что все интерактивы работают без сети, а клавиши стрелок листают слайды.

Зачем

Без истории откат — это бэкап, с Git — команда

Git превращает «откатить» из аварийной процедуры в обычную операцию.

😖 Без системы контроля версий

  • История в папках project_final_v2_ПРАВКИ_ok/
  • Непонятно, кто и зачем поменял строку, из-за которой упал прод
  • Два человека не могут править один проект без ручной склейки
→

😌 С Git

  • Каждое изменение с автором, датой и сообщением
  • Любая версия воспроизводится по её идентификатору
  • Откат — обычная операция: git revert
💡
АналогияКоммит — не список правок, а фотография всего проекта в конкретный момент. Поэтому любые два момента можно сравнить между собой.
🌐

Распределённость

У каждого — полный репозиторий с историей. Коммит, ветка, лог и откат работают без сети.

📸

Снимки, а не дельты

Каждый коммит хранит состояние всего дерева; неизменённые файлы переиспользуются.

#️⃣

Адрес = хеш содержимого

Изменилось содержимое — изменился идентификатор. Историю нельзя подправить незаметно.

Показать две картинки: папку «final_v2_ПРАВКИ_ok» и граф коммитов. Спросить зал, кто видел первое у себя.

Главная мысль: Git — это не «сохранялка», а история с авторами и откатами.

Ключевая идея

Git видит три зоны, а не две

Между файлами и историей стоит индекс — это то, что войдёт в следующий коммит.

Рабочий каталог

Файлы, которые вы правите в редакторе.

working directory

Что не в индексе: git diff
git addв индекс

Индекс

Подготовленный снимок: что войдёт в коммит.

staging area

Что уйдёт в коммит: git diff --staged
git commitв историю

Репозиторий

Неизменяемые коммиты в .git.

history

История: git log --oneline

Назад: git restore (диск ← индекс), git restore --staged (индекс ← репозиторий), git reset.

originудалённый репозиторий: git push отправляет, git fetch скачивает. Локальная работа без сети не требует origin.

Объекты и указатели

    
Ветка — это указатель на коммит, а не копия файлов

    
Создать ветку стоит почти ничего: это запись на 41 байт с хешем коммита.

  

  

    

      
      
💡
41 байт40 hex-символов хеша SHA-1 и перевод строки. Ни одного скопированного файла.

    

    

      
C
Коммит
Снимок всего дерева файлов + автор, дата, сообщение, ссылка на родителя.

      
B
Ветка
Подвижный указатель на один коммит: refs/heads/main.

      
H
HEAD
«Где я сейчас». Обычно ссылка на ветку, а не на коммит.

      
D
Detached HEAD
HEAD смотрит прямо на коммит: новые коммиты не привязаны к ветке и легко теряются.

      
T
Тег
Неподвижная метка. Для релизов используйте annotated tag.

      
O
origin
Просто имя URL, из которого клонировали. Не «главный сервер».

    

  

  

    
Ключевая фраза: ветка — подвижный указатель. Создали ветку — ничего не скопировали, просто записали хеш.

    
Спросить: что случится с коммитом, если HEAD «отвязан»? Ответ — он висит без ветки и уйдёт при переключении.

  







  

    
Ветки

    
Merge сохраняет историю, rebase переписывает её

  

  

    

      
      
      
    


    

      
    

    

      
    

    

      
    


    
Fast-forward: в main не появилось новых коммитов, поэтому слияние — это просто перенос указателя. Merge-коммита нет, история линейна.

    
Merge: обе ветки получили коммиты, Git создаёт merge-коммит с двумя родителями. История сохранена как была.

    
Rebase: коммиты feature переписаны поверх main с новыми хешами. История линейна, но переписана. Поэтому — только для неопубликованных веток.

  

  

    
Переключить вкладки по порядку: fast-forward, merge, rebase. На каждой показать, сколько родителей у результата.

    
Главное правило слайда: rebase переписывает хеши. Если ветку уже видел кто-то ещё, rebase ломает у него историю.

  







  

    
Конфликт

    
Конфликт — не авария: Git просто просит решить

    
Нажмите на блок кода или листайте →: подсвечивается шаг и пояснение справа.

  

  

    

      
    

    

      
1
Список конфликтов
UU — файл в конфликте. Git не угадывает: он остановился.

      
2
Правка маркеров
Уберите <<<, ===, >>>, оставьте верный код. Сверху — ваша ветка (HEAD), снизу — вливаемая.

      
3
git add
Означает «конфликт разрешён» для этого файла.

      
4
git commit
Создаёт merge-коммит. Передумали — git merge --abort.

    

  

  

    
Пройти четыре шага стрелкой. Подчеркнуть: маркеры одинаковы и при merge, и при rebase, отличается итоговая история.

    
Фраза для зала: «Конфликт — это вопрос, а не ошибка».

  







  

    
Практика

    
Ежедневный цикл: проверить, добавить, зафиксировать

    
Пять команд вокруг каждого коммита: посмотреть, отобрать, проверить, зафиксировать, сверить граф.

  

  

    

      
    

    

      
1
Что изменилось
Две колонки статуса — индекс и рабочий каталог. Строка ## — ветка и отставание от origin.

      
2
Кусок за куском
add -p кладёт в индекс только нужные фрагменты.

      
3
Что уйдёт в коммит
diff --staged — индекс против HEAD, ровно содержимое коммита.

      
4
Коммит
Индекс становится снимком. Сообщение — в императиве, с ответом «зачем».

      
5
Проверка графа
Все ветки и коммиты в одном виде. Ошибки видны до push.

    

  

  

    
Пройти пять шагов. Спросить зал: какой из них чаще всего пропускают? Обычно это status и diff --staged.

  







  

    
Проверка

    
Что попадёт в коммит?

  

  

    

      
      
Первая колонка статуса — индекс, вторая — рабочий каталог.

    

    

    

      
Вы поправили app.py и utils.py, но выполнили только git add app.py. Что войдёт в git commit?

      

        
        
        
      

      
Почему так. Коммит фиксирует индекс, а не диск. Индекс — это то, что вы подготовили через git add. Поэтому utils.py останется в рабочем каталоге до следующего коммита.

      

    

    

  

  
Дать 20 секунд подумать. Самый частый ответ — «оба», это и есть проверка понимания индекса.

Что случилось → какая команда отменит

    
Нажмите на ситуацию: появится команда. Почти всё в Git обратимо, нужно выбрать правильный инструмент.

  

  

    
    
    
    
    
    
  

  

    
Пройти шесть карточек, каждую открыть самим залом. Спросить: какая из них опасна? Ответ: reset --hard — незакоммиченное не вернуть даже reflog-ом.

Пять проверок перед коммитом

    
Отмечайте по ходу: полминуты проверки экономят часы чистки истории.

Попросить зал назвать шестой пункт. Обычно из зала приходит «git push», это хороший повод сказать: push — после всех пяти.

  







  

    
Проверка

    
Баг уже в общем main. Что делаем?

  

  

    

      
    

    

    

      
Коммит с багом уже отправлен в общую ветку main, и коллеги его забрали. Какая последовательность правильна?

      

        
        
        
      

      
Почему так. В общей ветке история не переписывается: revert добавляет обратный коммит, его можно просто отправить. Остальные варианты переписывают то, что коллеги уже забрали. --force-with-lease лишь не затрёт чужие новые коммиты — хеши всё равно поменяются.

      

    

    

  

  
Дать 20 секунд. Разобрать, почему «force-with-lease» не равно «безопасно для общей ветки».







  

    
Страховка

    
Reflog спасает почти всё, но не всё

    
Журнал всех перемещений HEAD: «потерянный» коммит почти всегда можно найти и вернуть веткой.

  

  

    

      
    

    

      
⚠ Что reflog не спасёт. Незакоммиченные правки, снесённые reset --hard или clean -fd: объектов в Git для них не было.

      
Границы страховки
    
        
  • Reflog локален: в свежем клоне его нет.
    • 
        
  • Записи истекают: 90 дней для достижимых коммитов, 30 — для недостижимых.
    • 
      

      
Дешёвая страховка
    
        
  • Перед рискованной операцией — git stash или git switch -c backup.
    • 
        
  • Это дешевле, чем героическое восстановление.
    • 
      

    

  

  

    
Показать вывод reflog и спросить: какая строка — «до катастрофы»? Ответ: вторая, это состояние до reset.

    
Подчеркнуть вторую половину слайда: reflog не спасает то, чего никогда не было в Git.
