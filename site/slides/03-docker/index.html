Зачем

Окружение должно ехать вместе с кодом

Без этого зависимость от машины живёт в головах людей, а не в репозитории.

😖 Без контейнеров

  • Версии Python, Node и glibc различаются по машинам
  • Инструкция по настройке устаревает раньше, чем её дочитали
  • Два сервиса на одном хосте спорят за версии пакетов
→

😌 С Docker

  • Окружение описано Dockerfile в том же репозитории
  • Один и тот же образ идёт через CI, staging и production
  • Весь стек поднимается командой docker compose up
📦
АналогияКак опломбированная коробка: содержимое не пересобирают по дороге от склада до магазина.
Docker решает упаковку и запуск на одной машине. Раскатка на 40 серверов, самовосстановление и автомасштабирование — задача оркестратора. Об этом в конце колоды.

Левая колонка — то, что знакомо каждому. Правая — что меняется. Подчеркнуть: один и тот же образ байт в байт идёт через CI, staging и production, никаких пересборок под окружение.

Контейнеры vs ВМ

Контейнер — процесс с границами, а не мини-ВМ

У каждой ВМ — своя ОС целиком. У контейнера ОС нет: только приложение с библиотеками поверх общего ядра хоста.

ВМ контейнер · шкалы условные, точные числа — в мануале.

Стандартная продакшен-схема — контейнеры внутри ВМ: ВМ даёт границу между клиентами, контейнеры дают упаковку и плотность.

Сначала показать стек ВМ: у каждого приложения своя ОС. Переключить на контейнер и сказать: ядро одно, а процесс — обычный, просто с ограничениями. Итог: контейнер мягче по изоляции, поэтому для жёсткой границы между клиентами ставят ВМ.

Словарь

Рецепт, образ, контейнер, склад

Один образ порождает сколько угодно контейнеров — как один бинарник порождает процессы.

📝
Dockerfile
Текстовый рецепт сборки. Аналогия: исходный код.
🧱
Image — образ
Неизменяемый набор слоёв и метаданных запуска. Аналогия: скомпилированный бинарник.
▶️
Container — контейнер
Запущенный экземпляр образа с writable-слоем сверху. Аналогия: процесс.
🏬
Registry — реестр
Хранилище образов с версиями и правами. Аналогия: артефакторий.
🔨docker buildDockerfile + контекст → образ
⬆️docker pushобраз → реестр
⬇️docker pullреестр → любой хост
▶️docker runобраз → контейнер
Почему образ переносим. Формат образа, runtime и протокол реестра стандартизированы OCI. Образ, собранный Docker, запустится в containerd, CRI-O или Podman.

Главная мысль: образ неизменяем, контейнер — его запущенная копия. Аналогии из обычной разработки помогают: исходник, бинарник, процесс, артефакторий. Затем пройти ряд команд: build → push → pull → run — это весь жизненный цикл образа. Про OCI сказать одной фразой, без подробностей.

Архитектура

Что происходит после docker run

Нажмите на этап: кто за него отвечает.

docker CLI

Всего лишь тонкий клиент: отправляет HTTP-запросы демону через Unix-сокет /var/run/docker.sock.

dockerd

Владелец всего состояния: образов, контейнеров, сетей и томов. Сборку отдаёт BuildKit. Работает от root.

containerd

Управляет жизненным циклом контейнеров и образов. Отдельный проект CNCF, который Kubernetes использует напрямую.

runc

Эталонная реализация OCI Runtime Spec: разворачивает namespaces и cgroups и запускает ваш процесс.

Запомните: dockerd работает от root. Поэтому доступ к сокету равен root-доступу к хосту. Вернёмся к этому в разделе про безопасность.

Пройти этапы слева направо по стрелке. Ключевой момент — root у демона и сокет. Это станет главным аргументом в разделе про безопасность.

Сборка и кэш

Порядок инструкций решает, что пересобирается

Меняйте код или зависимости кнопками и смотрите, какие слои уйдут в пересборку.

слоёв пересобрано
примерно на сборку

из кэша — слой не менялся. пересобран — изменился сам или слой выше. долго — дорогой шаг.

Кэш рвётся с первого изменённого слоя и тянет за собой всё ниже. Поэтому редко меняющееся — выше.

Сначала ничего не трогать: всё из кэша. Нажать «Правка кода» при порядке манифестов первыми — пересобрались два слоя. Включить переключатель «код раньше манифестов» и повторить: npm ci пересобирается тоже. Справа видно цену: ~10 секунд против 2–3 минут на каждую правку (оценки из мануала).

Multi-stage

Компилятор остаётся на стадии сборки

Переключите режим: сравните размер образа до и после.

Один образ: тулчейн внутри

≈ 800 МБ — размер стадии build. В образе остаются компилятор, исходники и инструменты сборки.

Multi-stage: только бинарник

≈ 15 МБ — в distroless/static попадает только бинарник через COPY --from=build. На той же шкале это 2% полосы.

Стадии, которые не нужны для --target, не собираются вовсе. Независимые стадии BuildKit строит параллельно.

Открыть код: стадия build тяжёлая, финальная — почти пустая. Переключить режимы: полоса 800 МБ против полоски в 15 МБ. Объяснить, что single-stage образ с тулчейном весит столько же, сколько стадия сборки.

Сети

В своей сети контейнеры находят друг друга по имени

Во встроенной сети контейнеры друг друга по имени не видят. Адрес соседа приходится искать вручную.

В user-defined bridge Docker поднимает встроенный DNS: имя сервиса резолвится, IP не нужен.

ДрайверКогда
bridgeодиночные контейнеры на одном хосте
user-definedгруппа сервисов, DNS по имени
hostсеть хоста, изоляции нет

-p 127.0.0.1:8080:3000 публикует порт только на localhost. Без IP-префикса порт открыт наружу.

Переключить с bridge на user-defined и сказать: это ровно то, что делает Compose автоматически. Подчеркнуть, что порт публикуют только для входа извне, а соседи общаются по имени внутри сети.

Compose

Весь стек — в одном файле

Нажмите на сервис, чтобы увидеть его конфиг из примера мануала.

Что важно в схеме

  • Compose сам создаёт сеть: api ходит к db:5432 по имени
  • db не публикует порт наружу
  • depends_on с service_healthy ждёт готовности БД

Тома

Данные pgdata живут в named volume и переживают docker compose down. Удаляются только с -v.

Кликнуть по api: показать ключ build, порт на localhost, строку подключения с именем db. Затем db: порт не публикуется, данные в томе, healthcheck. Ключа version нет: он устарел и игнорируется.

Данные

Данные переживают контейнер только в томах

Writable-слой исчезает вместе с docker rm. Нажмите на тип хранения, чтобы увидеть флаг.

💾
Named volume
Управляется Docker. Данные БД и загрузки в проде.
📁
Bind mount
Путь с хоста. Удобно для исходников в dev, в проде опасно.
⚡
tmpfs
Только в RAM. Секреты и временные файлы, которые не должны попасть на диск.
Синтаксис --mount явнее -v: опечатка в пути не создаст пустой каталог на хосте молча.

Три механизма, три задачи. Кликнуть named volume — подсветится флаг с томом. Кликнуть bind — флаг с проброшенным файлом. Подчеркнуть: bind в проде привязывает контейнер к структуре каталогов хоста.

Реестры

В production деплоим digest, а не тег

Тег — ярлык, который можно перевесить. Digest — адрес по содержимому.

⚠️

Плавающий тег

latest, main
  • Сегодня myapp указывает на один образ, завтра — на другой
  • Два хоста, сделавшие pull в разное время, работают на разных версиях
  • Откат ненадёжен: откатываться не на что
VS
🔒

Digest или SHA коммита

неизменяемая координата
  • myapp@sha256:9b2c… — адрес по содержимому, не меняется
  • Деплой ссылается на одну и ту же сборку на любом хосте
  • Теги оставляем людям для чтения
app:sha-9b2c1f4

Уникальный и неизменяемый: на него опирается деплой в production.

app:1.4.2

Семантическая версия — чтобы людям было удобно читать релизы.

app:main

Плавающий тег — только для dev- и staging-стендов.

Тег — для людей, digest — для деплоя.

Спросить зал, какой тег стоит в их проде. Затем показать разницу между изменяемым тегом и digest. Правило: latest — только для песочниц.

Дальше

Docker — фундамент, оркестратор — следующий этаж

Когда одного хоста и Compose мало, образ остаётся тем же. Меняется только то, что его запускает.

1

docker run

Один контейнер на одной машине.

2

docker compose

Несколько сервисов на одном хосте: локальная разработка и небольшой стенд.

3

Оркестратор

Kubernetes, Nomad, ECS: много узлов, самовосстановление, автомасштабирование.

Docker Compose не раскатывает на несколько хостов, не перезапускает нагрузку при падении узла и не делает rolling update с health-гейтами.

Качество образа окупается дважды: локально и в кластере.

Провести границу: Docker решает упаковку и запуск на одной машине, оркестратор — всё, что касается парка узлов. Анонсировать тему про Kubernetes как следующий шаг.

Проверка

Два вопроса по тому, что мы разобрали

Контейнер запущен с shell-формой CMD node main.js. Что будет при docker stop?
Почему так. Shell-форма ставит оболочку PID 1, а она сигналы не пробрасывает. Exec-форма CMD ["node", …] делает процесс PID 1, и он получает SIGTERM сам.
Где хранить данные Postgres, чтобы они пережили пересоздание контейнера?
Почему так. Named volume управляется Docker и переживает docker rm. Writable-слой исчезает вместе с контейнером, tmpfs живёт только в RAM.

Дать 20 секунд подумать на каждый вопрос, потом открыть разбор. Первый вопрос связывает сигналы и exec-форму, второй — типы хранения.
