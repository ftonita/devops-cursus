Тема 05 · Git-workflow для команд

Правила, которые
защищают main сами

Без договорённости ветки живут неделями, PR одобряют «LGTM» не глядя, а hotfix забывают влить обратно.

За ≈ 15 минут разберём стратегии ветвления, путь изменения до production, защиту main, релизы и hotfix. Большую часть покажем руками.

Начните с вопроса в зале: «Кто в команде знает, какая ветка сейчас в production?» Обещание темы: после презентации участники смогут выбрать стратегию, настроить защиту main и пройти hotfix без паники. Цифры в статистике взяты из мануала, на них можно ссылаться.

Зачем

Без договорённости main становится полем боя

Git одинаково легко даёт и порядок, и хаос. Что выйдет у вас, решают правила, а не инструмент.

😖 Без workflow

  • Ветки живут неделями, слияние превращается в merge hell
  • PR на 3000 строк «смотрят» за пять минут
  • Push в main в обход тестов и review
  • Hotfix сделан на сервере и забыт в ветке
→

😌 С согласованным workflow

  • Изменения маленькие и вливаются в main ежедневно
  • Проверки и одобрения гарантирует платформа, а не честное слово
  • main всегда зелёный, из него выпускается релиз
  • Срочный fix идёт по заранее отрепетированному пути
💡
АналогияGit — это дорога без светофора и разметки: ехать можно куда угодно, но столкновения неизбежны. Workflow и есть светофор, только вешаете его вы в настройках платформы.

Пройдитесь по левой колонке и спросите зал, какая из четырёх проблем знакома. Правая колонка — не список пожеланий, а то, что дают правила платформы. Подчеркните: «честное слово» заменяется техническим ограничением.

Модель

Workflow — это четыре слоя, и путать их не надо

У каждого слоя свой вопрос. Ответ на один не отвечает на другой.

вопрос 1

Стратегия ветвления

Какие ветки есть и сколько живут?

Пример: только main и ветки на 1–2 дня.

вопрос 2

Процесс интеграции

Как изменение попадает в main?

Пример: PR, 1 approval от CODEOWNERS, зелёный CI, merge queue.

вопрос 3

Метод слияния

Какой след оставляет изменение в истории?

Пример: squash, заголовок PR в формате Conventional Commits.

вопрос 4

Релизный процесс

Как из истории получается версия?

Пример: тег vX.Y.Z и changelog, сгенерированный из коммитов.

Метод слияния — не стратегия ветвления. Trunk-based и squash-merge прекрасно совместимы: решения независимы, хотя и влияют друг на друга.

Главная мысль слайда: слои не надо смешивать. Если кто-то спорит «у нас GitFlow», спросите, какой слой он имеет в виду. Пример на четвёртом слое пригодится на слайде про релизы.

Стратегии

Одна ось: сколько веток живёт и как долго изменение живёт отдельно

Переключайте стратегии: слева граф веток, справа плюсы, минусы и кому подходит.

Trunk-based Development

Плюсы

  • Почти нет merge hell
  • Минимальный Lead Time
  • Прямой путь к Continuous Deployment

Минусы

  • Нужен быстрый и надёжный CI
  • Нужны feature flags
  • Нужна культура маленьких PR

Подходит: SaaS, Continuous Deployment, зрелые команды.

GitHub Flow

Плюсы

  • Одно правило: всё в main можно деплоить
  • Простой дефолт без лишних веток
  • Hotfix — обычный PR с приоритетом

Минусы

  • Незаконченная работа чаще держится в ветке
  • Ветки легко зажить на недели

Подходит: веб-сервисы, небольшие и средние команды.

GitFlow

Плюсы

  • Явные релизы и фаза стабилизации
  • Удобно при плановом QA перед релизом
  • Ветки release и hotfix изолируют риски

Минусы

  • Две долгоживущие ветки: интеграция откладывается
  • Двойные merge hotfix легко забыть
  • Лишний слой для веб-сервиса с частыми деплоями

Подходит: коробочный софт, мобильные приложения, релизы по расписанию.

Release branches

Плюсы

  • Поддержка нескольких версий параллельно
  • Новые фичи не попадают в поддерживаемые ветки

Минусы

  • Каждый fix переносится cherry-pick'ом
  • Ветка никогда не вливается обратно в main

Подходит: мобильные приложения (ревью в сторе занимает дни), on-premise, библиотеки с LTS.

Дайте участникам 30 секунд: пусть сами нажмут все четыре вкладки. Ключевой вопрос к залу: «Что вы выберете для веб-сервиса с деплоем каждый день?» Главная ось сравнения — сколько долгоживущих веток и как долго изменение живёт отдельно от main.

Незаконченная работа

Деплой и релиз — разные события, и их разводит feature flag

Без флага незаконченная фича вынуждена жить в отдельной ветке. С флагом её можно влить в main уже сегодня.

Деплой: техническое событие

Новая версия кода запущена в production.

Релиз: продуктовое событие

Пользователи реально получили новую функциональность.

💡
АналогияДом построен и подключён к сетям (деплой), но въехать можно, когда открыли подъезд (релиз).

Типы флагов и срок жизни

  • Release toggle: скрыть незаконченное, включить готовое. Дни–недели, потом удалить.
  • Experiment toggle: A/B-тест. Живёт, пока идёт эксперимент.
  • Ops toggle (kill switch): быстро отключить рискованную функцию при инциденте. Может жить долго.
  • Permission toggle: функция для бета-тестеров или внутренних пользователей.
Правило: задача на удаление флага создаётся вместе с флагом. Иначе флаги становятся техническим долгом с отсроченным платежом.

Это самая «продающая» мысль для DevOps: деплой можно делать часто и безопасно, а релиз — решением продукта. Если спросят про всё, что флагом не спрятать, ответьте: изменение схемы БД и ломающее изменение API — через expand/contract и branch by abstraction.

Путь изменения

От задачи до production: нажмите на этап

Один путь, одна схема для trunk-based и GitHub Flow с merge queue. Остальные стратегии — вариации этой схемы.

Задача в трекере

Ключ задачи (например, PROJ-123) попадает в имя ветки. Так трекер сам связывает задачу, ветку и PR.

Если пропустить: ветку и PR не связать с задачей, и разобраться, зачем изменение, становится сложно.

Короткая рабочая ветка

Формат feat/PROJ-123-oauth-login. Ветка живёт дни, а не недели. В строгом trunk-based — не дольше 1–2 дней.

Если пропустить: расхождение с main растёт, а слияние дорожает.

Pull Request маленького размера

Ориентир до 200–400 изменённых строк. В описании три ответа: что изменилось, зачем, как проверить. Незаконченное открывайте как draft, чтобы получить ранний фидбек.

Если пропустить: на диффе в 3000 строк review становится формальным: «LGTM».

Проверки и review

CI запускает lint, тесты и commitlint. CODEOWNERS назначает владельцев путей. Человек смотрит на логику, архитектуру и риски, а не на отступы.

Если пропустить: обязательные проверки перестают быть техническим ограничением.

Merge queue

Одобренные PR встают в очередь. Платформа проверяет каждый на временной ветке «main + этот PR + впереди стоящие» и вливает, только если CI зелёный.

Зачем: «зелёный PR + зелёный PR = красный main» перестаёт случаться.

main всегда зелёный, и CD забирает каждый коммит

Незаконченная фича уже в production, но выключена флагом: деплой есть, релиза нет. Так работает CD из мануала 02-cicd.

Вывод: изменение доходит до пользователей за дни, а не за недели ветки.

Нажимайте этапы слева направо и спрашивайте: «На каком этапе у вас сейчас простой?» Обратите внимание: на каждом шаге есть «что будет, если пропустить». Это и есть доводы для команды.

Слева правила защиты main, справа состояние PR. Мерж блокируется, как только нарушено хотя бы одно включённое правило.

Правила защиты main

Состояние PR

✓ Мерж пройдёт

    Попросите зал угадать результат до нажатия. Сначала нажмите «Сценарий»: мерж заблокирован, потому что approve сброшен. Потом выключите только Dismiss stale: мерж всё равно блокируется правилом про последний push. Вывод: оба правила держат вместе, поэтому и описаны в мануале как пара.

    Релизы

    Версию и changelog считает история, а не человек в конце спринта

    Выберите тип коммита из главной ветки: версия по SemVer пересчитается сама.

    1.4.2→1.4.3PATCH

    Исправление бага. Попадает в changelog в раздел исправлений.

    1.4.2→1.5.0MINOR

    Новая обратно совместимая функциональность. В changelog — как новая возможность.

    1.4.2→2.0.0MAJOR

    Несовместимое изменение. Обозначается «!» после типа или футером BREAKING CHANGE:.

    1.4.2→1.4.2без изменений

    Служебные изменения (chore, docs, refactor, test, ci) версию обычно не меняют.

    Тег, changelog и номер версии создаёт автоматика (release-please, semantic-release, git-cliff). Они не расходятся, потому что собраны из одной истории коммитов.

    Переключайте типы коммитов по очереди. Спросите: «Какой коммит поднимет MAJOR?» Ответ: только несовместимое изменение, и его можно обозначить либо «!», либо футером. Тип коммита здесь важнее его размера.

    Конфликты

    Тяжёлые конфликты рождаются из долгих веток и больших правок

    Команда не может отменить конфликты, но может сделать их маленькими и редкими.

    причина 1

    Долгоживущие ветки

    Расхождение с main растёт каждый день, а сложность слияния растёт быстрее линейной.

    Лекарство: ежедневная синхронизация с main и интеграция в main.

    причина 2

    Массовые механические правки

    Переименование или автоформатирование всего проекта, сделанное параллельно с работой.

    Лекарство: отдельный PR с анонсом и .git-blame-ignore-revs.

    причина 3

    Горячие файлы

    Общий конфиг, реестр роутов, файл зависимостей, который правят все.

    Лекарство: регистрация через каталоги и автообнаружение вместо одного общего списка.

    Полезный инструмент: git rerere запоминает, как вы разрешили конфликт, и при повторном таком же применяет решение сам. Включается через rerere.enabled true.

    Здесь уместно спросить зал, у кого был «merge hell» на неделю. Почти всегда причина в одной из трёх строк карточек. Подчеркните: если долгая ветка уже есть, её надо синхронизировать с main минимум раз в день, а не ждать финального слияния.

    Hotfix

    Hotfix: сначала в main, потом cherry-pick в релизную ветку

    Сценарий: в v1.4.2 упал платёжный сервис. Пройдите шаги и посмотрите, что ломается при неверном порядке.

    Fix уже влит в main через обычный PR. Здесь нельзя «поправить на сервере»: иначе следующий релиз вернёт баг.

    -x дописывает в сообщение строку «cherry picked from commit», и по ней видно, откуда пришло изменение. Если ветка защищена, пуш делается через PR.

    Push тега запускает релизный пайплайн. Версия PATCH: 1.4.2 → 1.4.3.

    Что ломается: fix сделан только в release/1.4 и выкачен в прод. Через месяц плановый релиз собирается из main, а в main этого fix'а не было никогда. Баг возвращается.

    Как правильно: сначала main, потом cherry-pick вниз. Порядок «upstream first» исключает саму возможность такой регрессии.

    Пройдите шаги 1–3 как рецепт, а на шаге 4 остановитесь и спросите зал, что случится в следующем релизе. Порядок «main, потом cherry-pick» — главный вывод слайда. Hotfix не отменяет защиту веток: для срочного случая нужен быстрый путь review, а не обход.

    Ошибки

    Что ломается и как правильно: нажмите на карточку

    Шесть ошибок, которые встречаются почти в каждой команде.

    Дайте участникам по карточке, пусть сами угадают решение, и только потом откройте. Последняя карточка связана с предыдущим слайдом. Если в команде узнали себя хотя бы в одной ошибке, это уже хороший повод для ретроспективы.

    Формальный review: «LGTM» не глядя

    Баги проходят, откат затрагивает всё сразу.

    внимание упало
    Главный управляемый рычаг — размер PR. Он одновременно ускоряет review, снижает риск конфликтов и улучшает сразу несколько DORA-метрик.

    Метрики — только на уровне команды

    Как только PR cycle time становится личным KPI, работает закон Гудхарта: люди дробят PR ради цифры, а ревьюеры одобряют не читая. Обсуждайте тренд на ретроспективе.

    Нажмите три варианта размера подряд и спросите: «Где у вас сейчас?» Цифры — ориентиры, а не законы: их задаёт команда. Закрывайте слайд предупреждением про личные KPI: это самая частая причина, по которой метрики портят процесс.

    Практика

    Защиту main храните как код: её видно на review и её нельзя «забыть»

    Нажимайте блоки кода или листайте стрелкой: подсвечивается нужный фрагмент и пояснение справа.

    1
    Ruleset
    PR обязателен, 1 approval, сброс старых approve, linear history: JSON в репозитории.
    2
    Проверка
    API показывает, что правило действует, а не только описано в wiki.
    3
    Имена проверок
    Если не совпадут, required check никогда не отчитается и PR зависнет.

    Пройдите три шага стрелкой. Главная мысль: правила в JSON видны на review и одинаковы во всех репозиториях. Для одного сервиса хватит мышки, но с ростом команды настройки должны переехать в код.

    Проверка

    Что сломается в этих ситуациях?

    Срочный fix внесли только в release/1.4 и выкатили в прод. Через месяц плановый релиз собирают из main. Что произойдёт?
    Почему так. Fix сначала делают в main (upstream first), потом cherry-pick вниз. Релиз из main включает только то, что в main.
    В команде включили merge queue, но в CI не добавили триггер merge_group. Что будет?
    Почему так. Очередь проверяет результат слияния на временной ветке. Без merge_group обязательная проверка там не запускается, и PR остаётся в очереди навсегда.

    Дайте 20 секунд подумать над каждым вопросом, потом откройте разбор. Первый вопрос проверяет порядок hotfix, второй — понимание merge queue. Если зал ошибается на первом, вернитесь к слайду про hotfix.
